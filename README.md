# s21_mpfr

> **Status:** 🟢 **v1.19.0 (2026-10-15).**
> Библиотека чисел с плавающей точкой произвольной точности на C11.
> Вдохновлено [MPFR](https://www.mpfr.org/), но реализуется с нуля
> в учебных целях.

Собственная реализация библиотеки чисел с плавающей точкой
произвольной точности. Продолжение проекта
[s21_math](https://github.com/pavel-maru/s21_math), где мы
упирались в ограничения `long double` (80/128/64 бит).
Здесь эти границы убираются полностью — точность задаёт
пользователь.

## Что уже готово

- Тип `s21_mpf_t` — число произвольной точности (мантисса от 2 бит).
- `init`, `init2`, `clear` — управление жизненным циклом.
- `set_prec`, `set_prec_round` — in-place смена точности
  с сохранением значения; `set_prec` использует RNDN при сужении,
  `set_prec_round` принимает явный режим округления.
- `set_ui`, `set_si`, `set_d`, `set_str` — присваивание из базовых
  типов и из строк.  `set_str` работает в любом основании
  от 2 до 36, алфавит `0-9a-z` (регистронезависимо на входе).
- `set_zero`, `set_inf`, `set_nan` — специальные значения.
- `set`, `set_round` — присваивание с режимами округления
  RNDN / RNDZ / RNDU / RNDD.
- `cmp`, `cmp_abs`, `equal`, `zero_p`, `integer_p` — сравнения,
  включая корректную работу на числах разных точностей.
- `add`, `sub`, `mul`, `div`, `neg`, `abs` — базовая арифметика,
  корректная при любой точности (включая некратные 64).
  Умножение — Карацуба (O(n^1.585)) выше порога 32 лимба,
  schoolbook ниже.
- `sqrt`, `exp`, `log` — элементарные функции.
- **`pow`** — возведение в степень с семантикой C99 / MPFR,
  включая полный набор правил для `0`, `±inf`, `NaN`
  и знака нуля при нечётном целом показателе.
- **`pow_ui` / `pow_si`** — целочисленный показатель.  Бинарное
  возведение в степень без `exp`/`log`: точнее общего `pow`
  и не теряет guard-битов.
- **`root`** — корень n-й степени; `n = 1`, `2` обрабатываются
  напрямую, общий случай через `exp(log|x| / n)`.
- **`log2` / `log10`** — логарифмы по основаниям 2 и 10.
  `log2` использует reduction по степеням двойки и точен
  на `x = 2^m`.
- **`hypot`** — евклидова норма `√(x² + y²)` с масштабированием
  на `max(|x|, |y|)`.
- `pi`, `ln2`, `e` — публичные константы. **π считается через
  Borwein / Gauss-Legendre AGM** (квадратичная сходимость,
  ~12 итераций вместо ~900 членов Machin).
- `sin`, `cos`, `tan` — прямые тригонометрические функции.
- `atan`, `asin`, `acos` — обратные тригонометрические функции.
- **`sinh`, `cosh`, `tanh`, `asinh`, `acosh`, `atanh`** — все
  шесть гиперболических функций с корректной обработкой
  доменов, короткими замыканиями на малых и больших `|x|`
  и guard-битами против сокращения в `sinh`/`tanh`.
- **`*_with_pi`** — варианты всех шести тригонометрических функций,
  принимающие уже вычисленную π параметром.  Контракт:
  `pi->prec >= res->prec + 128 + E`, где `E = max(0, x->exp - 1)`.
- `print`, `print_d`, `get_str` — вывод: hex-мантисса, `double`-приближение,
  строка с заданным числом цифр и режимом округления в любом
  основании от 2 до 36.
- Низкоуровневые утилиты: `get_bit`, `set_bit`, `msb`, `lsb`.
- `s21_mpf_repl` — интерактивная утилита с кэшем π на текущую
  точность и с учётом E аргумента.
- `s21_mpf_bench` — микробенчмарк операций, включая сравнение
  тригонометрии с явной π и без; до `prec = 16384`.
- Unit-тесты в `src/test.c`: 49 групп, с автоподсчётом в финале;
  ULP-диагностика до `prec = 2048`.

Произвольное основание в `set_str` / `get_str`.  Один коммит:
362 вставки / 103 удаления в трёх файлах (`s21_mpf.h`,
`s21_mpf_io.c`, `test.c`).

- **Диапазон base ∈ [2, 36].**  Раньше оба примитива принимали
  только 10, всё остальное отвергалось.  Теперь алфавит —
  `0-9a-z`, регистронезависимо на входе, строчные буквы
  на выходе.  Префиксы `0x` / `0b` / `0o` не принимаются:
  вызывающий передаёт `base` явно, как в MPFR.

- **`set_str`.**  Разбор цифр через `digit_value` /
  `is_digit_in_base` вместо `isdigit`; `pow_base_mpf(res, base, k)`
  вместо `pow10_mpf`.  Экспонента `e` / `E` — только для base 10.
  Для base ≥ 15 буква `e` — цифра, поэтому `"1e2"` в base 16
  читается как `1·16² + 14·16 + 2 = 482`.  Спецзначения
  (`inf`, `infinity`, `nan`) разбираются до цифр и во всех
  основаниях — они base-агностичны.

- **`get_str`.**  Оценка `E` через `1 / log₂(base)` вместо
  константы `log₁₀ 2`; нормализация `y ∈ [1, base)`; извлечение
  цифр делением на `base_val`; округление через `half = base/2`
  и carry через `(base − 1)`.  Выходной формат — без префикса,
  только цифры (плюс `-` для отрицательных); `exp_out` — как
  в MPFR, `value ≈ 0.DDDD × base^exp_out`.

- **Примеры:**

  | вход | base | значение |
  |---|---|---|
  | `"101"` | 2 | `5` |
  | `"1.1"` | 2 | `1.5` |
  | `"17"` | 8 | `15` |
  | `"777"` | 8 | `511` |
  | `"ff"` | 16 | `255` |
  | `"1.8"` | 16 | `1.5` |
  | `"1e2"` | 16 | `482` (не `100`) |
  | `"zz"` | 36 | `1295` |

- **Ошибки.**  `base` вне `[2, 36]` → `-1`.  Цифра вне базы
  (`'g'` в base 16, `'8'` в base 8, `'2'` в base 2) → `-1`.
  Префикс `"0x1"` в base 16 → `-1`, потому что `'x'` не цифра.
  `"1e"` в base 10 без цифр после экспоненты → `-1`.

- **Исправленный дефект.**  `set_str("0x1", 16)` изначально
  возвращал `0` (разбирал как ноль).  Ветка `!seen_nonzero`
  срабатывала **до** проверки хвоста `*p != '\0'`: после `'0'`
  `seen_nonzero` оставался нулевым, следующий символ `'x'`
  останавливал цикл, и функция возвращала ноль, игнорируя
  остаток строки.

  Фикс: проверка `*p != '\0'` переехала выше ветки
  `!seen_nonzero`.  После фикса `"0x1"` в base 16 и `"0abc"`
  в base 10 отвергаются, `"0"` и `"0.000"` остаются валидным
  нулём, `"-0"` сохраняет знак.

- **Одна новая тест-группа `test_base_conversion`.**
  Покрывает base 2, 8, 16, 36: целые и дробные значения,
  знаки, регистронезависимость на входе, экспонента только
  в base 10, спецзначения во всех основаниях, невалидные
  base, round-trip через `get_str` → `set_str`.
  Общее число групп: 48 → 49.

## Сборка

Все команды запускаются из каталога `src/`:

```sh
cd src
make                     # статическая библиотека libs21_mpf.a
make test                # собрать и запустить unit-тесты
make repl                # интерактивная утилита s21_mpf_repl
make bench               # микробенчмарк s21_mpf_bench
make clang-format        # применить clang-format ко всем исходникам
make clang-format-check  # проверить форматирование (для CI, без правок)
make valgrind            # утечки памяти (memcheck)
make asan                # сборка с AddressSanitizer
make ubsan               # сборка с UndefinedBehaviorSanitizer
make gcov_report         # покрытие (lcov + genhtml)
make clean               # удаление артефактов
```

Альтернатива без `cd` — из корня проекта:

```sh
make -C src test
```

Компилятор: `gcc`, стандарт `-std=c11`, флаги `-Wall -Wextra -Werror -O2`.
Стиль кода задан в `.clang-format` (Google Style, отступ 2 пробела).

## Как устроено внутри

### Представление числа

```c
typedef struct {
  uint64_t *limbs;   /* мантисса, little-endian, limbs[0] — младшие 64 бита */
  int64_t   exp;     /* x = (-1)^sign · mant · 2^(exp − prec) */
  uint32_t  prec;    /* точность в битах */
  int       sign;    /* 0 = +, 1 = − */
  int       kind;    /* ZERO / NORMAL / INF / NAN */
} s21_mpf_t;
```

**Инварианты для NORMAL:** MSB мантиссы на позиции `prec − 1`,
биты выше `prec` нулевые, значение `x = (−1)^sign · mant · 2^(exp − prec)`.

**Специальные значения:** `ZERO` (хранит знак −0), `INF` (±), `NAN`.

### Нормализация и смена точности

`s21_mpf_normalize` приводит мантиссу к инварианту MSB@prec−1.
Сдвиги — единые функции `s21_mpf_shift_left_into` / `s21_mpf_shift_right_into`.

`s21_mpf_set_prec` меняет точность на месте, сужение — RNDN.
`s21_mpf_set_prec_round` — то же, но с явным режимом округления.
Обе разделяют подпрограммы `mpf_sticky_below`, `mpf_round_up`,
`mpf_add_one`.

### Стековые временные объекты

Обёртка `s21_mpf_stack_t` содержит `s21_mpf_t` и буфер
`uint64_t[S21_MPF_STACK_LIMBS]` (32 лимба = 2048 бит).  Применяется
в `add`, `sub`, `div`, `pow`, гиперболических и в `*_raw`.

### Scratch-пространство `mul_raw`

`mul_raw` использует единый буфер `total = 2·l_wp + l_prod` лимбов.
Если `total ≤ S21_MPF_MUL_SCRATCH_LIMBS` (512 лимбов = 4 КБ) —
стековый массив и один `memset`; иначе — один `calloc(total)`.
`temp.limbs` служит приёмником `mul_mant`, отдельный `prod` не нужен.

### Карацуба в `mul_mant`

Для `n < S21_MPF_KARATSUBA_THRESHOLD = 32` умножение делается
schoolbook — двойной цикл по лимбам с накоплением через
`unsigned __int128`.  Для `n ≥ 32` мантиссы расщепляются по формуле:

```
a = a1·B^h + a0,   b = b1·B^h + b0,   B = 2^64, h = floor(n/2)
a·b = a1·b1·B^(2h) + [(a1+a0)(b1+b0) − a1·b1 − a0·b0]·B^h + a0·b0
```

Три рекурсивных умножения размера `n/2` вместо четырёх.  Сложность
O(n^1.585).

Scratch для текущего уровня и всей рекурсии — единый пул,
распределяемый в `s21_mpf_mul_mant_karatsuba` одним `malloc(10n + 256)`.

Публичный cross-check: `s21_mpf_mul_mant_schoolbook` экспонирован
во внутреннем API для тестов.  `test_mul_karatsuba_vs_schoolbook`
сверяет оба пути побитово на 12 размерах.

### Borwein AGM π

Формула (Gauss-Legendre / Borwein & Borwein, «Pi and the AGM»):

```
a₀ = 1, b₀ = 1/√2, t₀ = 1/4, p₀ = 1
Итерация: a_{n+1} = (aₙ + bₙ) / 2
          b_{n+1} = √(aₙ · bₙ)
          t_{n+1} = tₙ − pₙ · (aₙ − a_{n+1})²
          p_{n+1} = 2 · pₙ
Результат: π = (a + b)² / (4 · t)
```

Сходимость квадратичная: число правильных бит удваивается
за итерацию.  ~12 итераций покрывают `wp = 4160` — против ~900
членов ряда `atan(1/5)` и ~260 членов `atan(1/239)` в формуле
Мэчина.

Внутренняя точность — `wp + 64`, запас на накопление ошибки
в 12 итерациях.  Финальное `(a + b)² / (4t)` считается на
`wp + 64`, и только потом сужается до `wp` через `set_round`.
Прямое `div_raw` в целевую `pi` теряло бы старшие 64 бита
операндов (см. «История дефектов v1.15.0»).

`_machin`-версия сохранена во внутреннем API для cross-check.

### Argument reduction в тригонометрии

`reduce_2pi(r, a, pi, wp)` сводит `a` к `(-π, π]` через
`r = a − round(a / 2π) · 2π`.  Если `a ≈ 2^E`, вычитание двух
чисел порядка `2^E` сокращает `E` старших бит: точность падает
с `2^-wp` до `2^(E-wp)`.

Хелпер `trig_extra_bits(x)` возвращает `max(0, x->exp − 1)`.
Это значение добавляется к рабочей точности в `sin_impl`,
`cos_impl`, `tan` — и к контракту `*_with_pi`.  При
`E > S21_MPF_MAX_ARG_BITS = 10000` функция возвращает NaN.

### Знак нуля в `pow`

`pow(±0, y)` даёт `±0` или `±inf`; знак результата —
`sign_x & (y mod 2)`.  Это согласуется с `1 / (−0)³ = −inf`
и с IEEE 754 `pow(−0, 3) = −0`.  Чётность `y` определяется
одним битом мантиссы: для нормализованного `y` бит на позиции
`prec − exp` имеет вес `2⁰` в значении, поэтому именно он
и есть младший бит целой части.

### Сокращение в гиперболических

`sinh(x) = (e^x − e^−x) / 2`.  При малых `|x|` оба слагаемых
почти равны, разность — порядка `2x`.  Потеря точности
`log₂(1/|x|)` бит.  Хелпер `hyp_exp_pair` добавляет к рабочей
точности `guard = min(−exp(x), prec)`.

`cosh` этой проблемы не имеет: оба слагаемых одного знака,
сумма — порядка `e^x`, дополнительных guard-битов не требуется.

`tanh` использует ту же защиту, что `sinh` (числитель
подвержен сокращению, знаменатель — нет).

### Основание в `set_str` / `get_str`

Обе функции обобщены на `base ∈ [2, 36]` через три хелпера:
`digit_value(c)` (символ → значение, `-1` вне алфавита),
`digit_char(d)` (значение → строчный символ) и
`is_digit_in_base(c, base)` (проверка «это цифра данной базы»).
Хелперы — статические, во внутренний API не экспонируются.

Парсинг экспоненты в `set_str` (`e` / `E`) работает только
при `base == 10`.  Для `base ≥ 15` буква `e` попадает
в разряд цифр, и разделитель экспоненты пропадает.  Это
осознанное упрощение — поддержка C99-hexfloat (`p`-экспонента
только в base 16) оставлена на будущее.

`get_str` использует `pow_base_mpf(res, base, k)` — обобщение
бывшего `pow10_mpf` — для масштабирования `y` к диапазону
`[1, base)`.

### Почему нет SIMD

`mul_mant_schoolbook` — единственный участок, где SIMD вообще
применим.  Карацуба и более высокоуровневая логика (`mul_raw`,
`div_raw`) работают с цепочками carry и рекурсией, которые
векторизуются плохо: переносы создают зависимости между
итерациями, а рекурсия — непредсказуемые обращения к памяти.

Schoolbook живёт при `n ≤ 32` (порог Карацубы).  Внутри `mul`
на `prec = 4096` это ~20% времени, на `prec = 16384` — около
25%.  SIMD дал бы ~1.5× на этой части, то есть **7–9% на `mul`
в целом** — за 300–500 строк платформозависимого кода, двух
реализаций (x86-64 + aarch64) и условной компиляции.  Для
учебного проекта это неоправданная сложность.

Реальные альтернативы для дальнейшего ускорения `mul` — ручной
ассемблер (`mulx`/`adcx`/`adox` в стиле GMP) или Schönhage-Strassen
FFT для `prec ≥ 10⁵`.  Обе за пределами текущего диапазона
и целей проекта.

### Алгоритмы по операциям

| Операция | Подход | Рабочая точность |
|---|---|---|
| `add`, `sub` | выравнивание по `exp`, сложение с carry / вычитание с borrow | `prec + 64` |
| `mul` | Карацуба выше 32 лимбов, schoolbook ниже | `prec + 64` |
| `div` | алгоритм D Кнута | `prec + 64` |
| `sqrt` | метод Ньютона с seed из `double` | `prec + 64` |
| `exp` | ряд Тейлора после halving до `\|y\| ≤ 2^-5` | `prec + 64` |
| `log` | atanh-ряд с `m = 5` sqrt reduction | `prec + 64` |
| `pow` | `exp(y · log\|x\|)`, знак отдельно | `prec + 64` |
| `pow_ui` | бинарное возведение, без `exp`/`log` | `prec + 64` |
| `pow_si` | `pow_ui` + обращение через `div_raw` | `prec + 64` |
| `root` | `exp(log\|x\| / n)`, знак отдельно | `prec + 64` |
| `log2` | reduction `x = 2^k · y`, `k + ln(y)/ln 2` | `prec + 64` |
| `log10` | `log(x) / ln(10)` | `prec + 64` |
| `hypot` | `m · √((x/m)² + (y/m)²)`, `m = max(\|x\|, \|y\|)` | `prec + 64` |
| `set_str` | поразрядный разбор, `pow_base_mpf` | `prec + 64` |
| `get_str` | `n_digits · log₂(base) + 192` | — |
| `pi` | Borwein / Gauss-Legendre AGM | `prec + 64` |
| `ln2`, `e` | `2·atanh(1/3)` / `exp(1)` | `prec + 64` |
| `sin`, `cos` | reduction по `2π`, затем ряд | `prec + 64 + E` |
| `tan` | `sin(x) / cos(x)` | `prec + 64 + E` |
| `atan` | reduction + степенной ряд | `prec + 64` |
| `asin`, `acos` | через `atan` / `π/2 − asin` | `prec + 64` |
| `sinh`, `tanh` | `(e^{±x} − e^{∓x}) / 2`, `sinh/cosh` | `prec + 64 + guard` |
| `cosh` | `(e^x + e^{−x}) / 2` | `prec + 64` |
| `asinh`, `acosh` | `log(x + √(…))` | `prec + 64` |
| `atanh` | `½·log((1+x)/(1−x))` | `prec + 64` |
| `set_round` | RNDN / RNDZ / RNDU / RNDD | `dst->prec` |
| `set_prec`, `set_prec_round` | in-place | `prec` |

**Guard-биты `prec + 64`** защищают значащую часть результата.
Для `sin`/`cos`/`tan` добавляется `E` из-за сокращения в reduction,
для `sinh`/`tanh` — `guard` из-за сокращения при малых `|x|`.

**Ленивое π** — вычисляется один раз на верхнем уровне и передаётся
в `_impl`-варианты.  Без глобального кэша в библиотеке.

**Knuth D в `div`** — O(n²) лимбовых умножений.

**Double seed в `sqrt`** — ~7 итераций Newton из ~14 при `prec = 4096`.

**Sqrt reduction в `log`** — пять `sqrt` сокращают ряд с ~1300
до ~300 членов при `wp = 4160`.

**Карацуба в `mul`** — O(n^1.585) выше 32 лимбов.

**AGM в `pi`** — квадратичная сходимость, ~12 итераций на любой
`prec`.

### Тригонометрия с явной π

Публичные `sin`/`cos`/`tan`/... при каждом вызове считают π заново.
С v1.15.0 это уже не 12 мс, а ~2 мс при `prec = 4096`, но всё
равно доминирует: сам ряд `sin`/`cos` — ~3.4 мс.

Если в цикле много тригонометрических вызовов, π стоит
посчитать один раз:

```c
uint32_t prec = 4096;
s21_mpf_t pi;
s21_mpf_init2(&pi, prec + 128);
s21_mpf_pi(&pi);

s21_mpf_t x, r;
s21_mpf_init2(&x, prec);
s21_mpf_init2(&r, prec);

for (int i = 0; i < 1000; i++) {
  s21_mpf_set_d(&x, i * 0.001);
  s21_mpf_sin_with_pi(&r, &x, &pi);   // без пересчёта π
}
```

Шесть публичных функций `*_with_pi` — тонкие обёртки над
существующими `_impl`-вариантами.  Контракт:
`pi->prec >= res->prec + 128 + E`.  Меньшая точность π даёт -1;
при `E > S21_MPF_MAX_ARG_BITS` — NaN.

### I/O

**`set_str`** — посимвольный разбор с накоплением мантиссы
в `prec + 64` бит.  Работает в любом основании от 2 до 36.
Финальное округление — RNDN.

**`get_str`** — оценка `E ≈ floor(log_base(x))`, масштабирование
через `pow_base_mpf`, нормализация в `[1, base)`, извлечение
цифр, округление RNDN / RNDZ / RNDU / RNDD.  Реализация
разбита на четыре подпрограммы: `get_str_special`,
`get_str_extract`, `get_str_should_round_up`, `get_str_round_up`.

требуют совпадения `prec` — чтение уходило за пределы мантиссы
`x`.  Проявилось как `acosh(2)`, отличающееся от `1.31696…`
в 14-й значащей цифре.  Фикс: `s21_mpf_set(&xw, x)` до начала

**v1.18.0**: **`pow_si` падал с FPE**.  Результат деления
`1 / pow_ui(x, |n|)` шёл напрямую в `res` с `prec = 256`, тогда
как операнды были инициализированы на `wp = 320`.  `div_raw`
читает только `limbs_for_prec(res->prec)` младших лимбов —
у 320-битного операнда старший лимб не попадал в `V`, и
`div_knuth` делил на ноль (`V[n-1] = 0`).  Симптом:
`Floating point exception (core dumped)` на `pow_si(2, -3)`.

Фикс: результат деления идёт в рабочий временный объект на `wp`,
спецзначения (`ZERO` / `INF` / `NAN`) отсеиваются **до** `div_raw`.
Финальный `s21_mpf_set` сужает `wp → res->prec` через RNDN.
Тот же паттерн, что в v1.17.0.

**v1.19.0**: **`set_str("0x1", 16)` разбирал как ноль**.  Ветка
`!seen_nonzero` срабатывала **до** проверки хвоста `*p != '\0'`:
после `'0'` `seen_nonzero` оставался нулевым, следующий символ
`'x'` не является цифрой base 16 и останавливал цикл, а функция
возвращала 0, игнорируя неразобранный остаток.  Та же ошибка
затрагивала `set_str("0abc", 10)` — «ноль» вместо `-1`.

Фикс: проверка `*p != '\0'` переехала **выше** ветки
`!seen_nonzero`.  После фикса `"0x1"` в base 16 и `"0abc"`
в base 10 корректно отвергаются, `"0"`, `"0.000"` и `"-0"`
остаются валидными.

### Теоретические оценки сложности

- `add`, `sub`, `cmp` — O(n);
- `mul` — O(n^1.585) (Карацуба), O(n²) ниже порога;
- `div` — O(n²);
- `sqrt` — O(n²) на итерацию, O(log n) итераций;
- `exp` — O(n²·k), `k ≈ wp/5`;
- `log` — O(n²·k), `k ≈ wp/(2m+2)`, `m = 5`;
- `pow` — стоимость `exp` + `log` + `mul`;
- `pow_ui` — O(log n) умножений;
- `pow_si` — стоимость `pow_ui` + `div`;
- `root` — стоимость `exp` + `log` + `div`;
- `log2` — стоимость `log_unit_interval` + `ln2` + `div`;
- `log10` — стоимость `log` + `div`;
- `hypot` — стоимость `sqrt` + 2 `div` + 2 `mul`;
- `set_str` — O(digits) `mul_raw` + O(digits) `add_raw` + одно `pow_base_mpf`;
- `get_str` — O(n_digits) делений;
- `pi` — O(M(n)·log n) — 12 итераций AGM, каждая — `sqrt` + `mul`;
- `sin`/`cos` — O(n²·k) по ряду + π;
- `sinh`/`cosh`/`tanh` — стоимость одного `exp` (плюс `div` для `tanh`);
- `asinh`/`acosh`/`atanh` — стоимость `log` + `sqrt`.

## Чек-лист структурного программирования

Проверка по семи принципам Дейкстры и их следствиям.  Состояние
после v1.19.0.

**Принципы:**

| № | Принцип | Статус |
|---|---|---|
| 1 | Отказ от `goto` | ✅ |
| 2 | Три базовые конструкции | ✅ |
| 3 | Произвольная вложенность базовых конструкций | ✅ |
| 4 | Логически целостные фрагменты выносятся в подпрограммы | ✅ |
| 5 | Каждая группа инструкций — блок | ✅ |
| 6 | Один вход, один выход | ⚠️ арифметика — ✅, спецзначения — ранние `return` |
| 7 | Разработка сверху вниз | ✅ |

**Следствия:**

| № | Следствие | Статус |
|---|---|---|
| 1 | Запрет глобальных переменных | ✅ (в REPL — статическое состояние утилиты) |
| 2 | Не более одного выхода из функции | ⚠️ см. принцип 6 |
| 3 | Не более одного выхода из цикла | ✅ |
| 4 | Вложенность блоков ≤ 4 | ✅ (максимум — 2) |
| 5 | Размер функций 40–50 строк | ⚠️ `div_knuth` (~55), `mul_mant_rec` (~50); на границе — `set_str`, `get_str`, `pow`, `pow_ui`, `root`, `hypot`, `sqrt`, `exp`, `atan_impl`, `cos_impl`, `tan_impl`, `pi_agm_iterate` |

**Комментарии к ⚠️:**

- **Pre-checks** — защита от некорректного вызова.
- **Ранние `return 0` на спецзначениях** — `*_special`-паттерн
  не подходит для функций, чьи `_impl`-варианты ожидают только
  `NORMAL`; `pow`, `pow_ui`, `pow_si`, `root`, `hypot`
  и гиперболические следуют тому же принципу.
- **`div_knuth`**, **`mul_mant_rec`** — структурно сложные функции
  с внутренними фазами алгоритма.  Каждая из них уже разбита
  настолько, насколько позволяет структура алгоритма.
- **`set_str`** выходит за 50 строк из-за двух циклов разбора
  (целая и дробная части) и нескольких веток валидации.  Часть
  кода повторяется в двух циклах — потенциальный кандидат
  на вынос общего хелпера `accumulate_digit(M, d, base, wp)`.
  Оставлено на будущий рефакторинг.

## Roadmap на будущее

- **Дальнейшие утилиты.**  `s21_mpf_log1p(x)` (точный `log(1+x)`
  для малых `x`), `s21_mpf_expm1(x)` (точный `exp(x) − 1`),
  `s21_mpf_cbrt(x)` (кубический корень — частный случай
  `root(x, 3)`, но с более быстрым путём без `exp`/`log`),
  `s21_mpf_fmod(x, y)`, `s21_mpf_floor` / `ceil` / `round` /
  `trunc` (публичные обёртки над существующей внутренней
  `s21_mpf_trunc`).

- **Hexfloat: C99-формат `0x1.8p4`.**  Сейчас `set_str` / `get_str`
  в base 16 работают, но без `p`-экспоненты.  C99-формат
  (цифры до и после точки, затем `p` и десятичная степень
  двойки) — стандартный способ точной записи double.
  Реализуется поверх существующих хелперов: `p` — разделитель,
  значение после него — десятичное число, дающее сдвиг экспоненты.

- **`s21_mpf_repl`: команды для не-десятичных баз.**  `hex` уже
  есть, но без base-специфичных команд вывода (`oct`, `bin`).
  Добавляются тривиально поверх `get_str(..., base, ...)`.

- **SIMD в `mul_mant_schoolbook` — рассмотрено, не окупается.**
  Schoolbook-путь вызывается только при `n ≤ 32` (ниже порога
  Карацубы).  Внутренний цикл — 32×32 = 1024 умножения,
  ~3000 тактов.  SIMD-версия через 32-битный split (SSE2,
  baseline x86-64) дала бы schoolbook-пути ~1.5×, что на
  полном `mul` составляет **7–9%**.  Цена: 300–500 строк
  платформозависимого кода, две реализации (x86-64 + aarch64),
  условная компиляция по уровню SIMD.  Экономика не сходится.

  Реальный путь к ускорению `mul_mant_schoolbook` — **не SIMD,
  а ручной ассемблер** (`mulx` + `adcx` + `adox` из BMI2/ADX,
  Haswell+ 2013+).  Это подход GMP, даёт ~2.5× на schoolbook
  против чистого C.  Но: только x86-64, только свежие CPU,
  теряется портативность.  Для учебного проекта — за пределами.

- **Toom-Cook 3-way** — пересмотреть только после появления
  ассемблерной версии `mul_mant_schoolbook`.  На чистом C11
  crossover выше 300 лимбов, что за пределами нашей рабочей
  области.  Реализация сохранена в истории (коммиты `9780945`
  и `d4e5f01`), откат — `4bb3947` и `9bd58b5`.  Замеры — в блоке
  v1.16.0.

- **Sasaki-Kanada AGM-log.**  Формула
  `ln x = π / AGM(θ₂²(1/x), θ₃²(1/x))` из статьи 1982 года.
  Не окупается на текущей архитектуре: нужна π внутри, а даже
  с AGM-π она стоит ~2 мс при `prec = 4096` против 3.2 мс всего
  `log`.  Может стать выгодной после ускорения π.

- **Binary splitting для atanh-ряда.**  Не окупается для mpf-аргументов:
  требует повышения точности до `wp + log₂(N!)`, что перевешивает
  выигрыш от divide-and-conquer.  Имеет смысл только для рациональных
  аргументов с малым числителем/знаменателем (например, для ln2,
  π через Machin), где у нас уже есть быстрые реализации.

## Мотивация

В `s21_math` мы делали `math.h` с точностью `long double`.
Предел — эффективная точность ~226 бит.  `s21_mpfr` снимает
это ограничение: точность задаётся пользователем от 2 бит
до миллионов.  Это позволяет вычислять `sin(1e10)` с точностью
`2^-1000`, реализовывать произвольную точность для криптографии
(RSA, ECC), экспериментировать без потери контроля над
форматом числа.
