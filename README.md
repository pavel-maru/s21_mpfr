# s21_mpfr

> **Status:** 🟢 **v1.12.0 (2026-10-13).**
> Библиотека чисел с плавающей точкой произвольной точности на C11.
> Вдохновлено [MPFR](https://www.mpfr.org/), но реализуется с нуля
> в учебных целях.

Собственная реализация библиотеки чисел с плавающей точкой
произвольной точности. Продолжение проекта
[s21_math](https://github.com/pavel-maru/s21_math), где мы
упирались в ограничения `long double` (80/128/64 бит).
Здесь эти границы убираются полностью — точность задаёт
пользователь.

## Что уже готово

- Тип `s21_mpf_t` — число произвольной точности (мантисса от 2 бит).
- `init`, `init2`, `clear` — управление жизненным циклом.
- `set_prec`, `set_prec_round` — in-place смена точности
  с сохранением значения; `set_prec` использует RNDN при сужении,
  `set_prec_round` принимает явный режим округления.
- `set_ui`, `set_si`, `set_d`, `set_str` — присваивание из базовых
  типов и из десятичных строк.
- `set_zero`, `set_inf`, `set_nan` — специальные значения.
- `set`, `set_round` — присваивание с режимами округления
  RNDN / RNDZ / RNDU / RNDD.
- `cmp`, `cmp_abs`, `equal`, `zero_p`, `integer_p` — сравнения,
  включая корректную работу на числах разных точностей.
- `add`, `sub`, `mul`, `div`, `neg`, `abs` — базовая арифметика,
  корректная при любой точности (включая некратные 64).
- `sqrt`, `exp`, `log` — элементарные функции.
- `pi`, `ln2`, `e` — публичные константы: π (формула Мэчина),
  натуральный логарифм 2, основание натурального логарифма.
- `sin`, `cos`, `tan` — прямые тригонометрические функции.
- `atan`, `asin`, `acos` — обратные тригонометрические функции.
- **`*_with_pi`** — варианты всех шести тригонометрических функций,
  принимающие уже вычисленную π параметром. Позволяет не считать π
  на каждый вызов в цикле (при prec = 4096 экономия до 4.2× для
  `sin`/`cos` и 2.6× для `tan`).
- `print`, `print_d`, `get_str` — вывод: hex-мантисса, `double`-приближение,
  десятичная строка с заданным числом цифр и режимом округления.
- Низкоуровневые утилиты: `get_bit`, `set_bit`, `msb`, `lsb`.
- `s21_mpf_repl` — интерактивная утилита с кэшем π на текущую
  точность.
- `s21_mpf_bench` — микробенчмарк операций, включая сравнение
  тригонометрии с явной π и без.
- Unit-тесты в `src/test.c`: 39 групп, с автоподсчётом в финале;
  ULP-диагностика до `prec = 2048`.

### v1.10.0 (2026-10-12)

Улучшенный argument reduction для `exp`/`log` и критический
фикс `exp`, найденный попутно.

- **`log`: m = 5 sqrt reduction.** К `y ∈ [1, 2)` применяется
  5 итераций `sqrt` перед построением `z = (y-1)/(y+1)`. Ряд
  `atanh(z)` сходится за ~`wp / (2m+2)` членов вместо
  ~`wp / log₂(9)`: для `wp = 4160` это ~300 vs ~1300.
  Стоимость 5 sqrt (~500 μs с v1.9.0 double seed) окупается
  шестикратно.
- **`exp`: halving до `|y| ≤ 2^-5`** вместо `|y| < 1`. Ряд
  Тейлора сокращается с ~`wp` до ~`wp/5` членов. Четыре
  дополнительных квадрата (по одной `mul`) дешевле ~200
  сэкономленных членов.
- **Фикс: обрезание ряда `exp`.** Внутри `exp` был жёсткий cap
  в 300 членов, заложенный с первой версии. При `prec ≥ ~3000`
  ряд для `exp(1.5)` требует больше — он молча обрезался.
  Заменено на `max_terms = wp + 10`.
- **`test_exp_log_extremes`**: `log(exp(±100))`, `log(10^10)`,
  `log(10^-10)`, `log(1 + 2^-50)`, `exp(a)·exp(-a) = 1`.
- **`test_ulp_diagnostics` расширен до N = 2048**.

### v1.11.0 (2026-10-12)

Оптимизация `mul_raw` через scratch-пространство. Побочный
эффект — ускорение всех трансцендентных.

- **`mul_raw` использует единый scratch-буфер** вместо четырёх
  динамических аллокаций (`xw`, `yw` при `wp = prec + 64`,
  `temp` при `2·wp`, плюс отдельный `prod`). Общий размер
  `total = 2·l_wp + l_prod`: 261 лимб при `prec = 4096`, 20 при
  `prec = 256`. Влезает в стековый буфер `S21_MPF_MUL_SCRATCH_LIMBS`
  (512 лимбов, 4 КБ) → `memset` + работаем; не влезает → один
  `calloc(total)` вместо четырёх.
- `temp.limbs` служит приёмником `mul_mant`, отдельный `prod`
  не нужен — экономит ~130 лимбов при `prec = 4096`.
- **`mul` и `div` приведены к одному `return`.** У `mul` было
  три выхода (pre-check, ошибка `mul_raw`, финальный 0);
  переписан на `rc`. У `div` возврат `div_raw` молча
  игнорировался — при OOM `res` получал ноль вместо ошибки;
  теперь `rc` проверяется перед `set`.

Ускорение по бенчмарку (x86-64, gcc -O2, best of 3):

|---|---|---|---|---|
| `mul` было | 242 ns | 325 ns | 982 ns | 7.67 μs |
| `mul` стало | 107 ns | 176 ns | 726 ns | 7.57 μs |
| ускорение | **2.26×** | **1.85×** | **1.35×** | 1.01× |
| `exp` было | 8.34 μs | 21.9 μs | 181 μs | 3.55 ms |
| `exp` стало | 4.99 μs | 17.0 μs | 156 μs | 3.46 ms |

### v1.12.0 (2026-10-13)

Расширение API точечными утилитами и критический фикс
аргумент-редукции для тригонометрии.

- **`set_prec_round(x, prec, rnd)`** — in-place смена точности
  с явным режимом округления. Раньше сужение в `set_prec` всегда
  использовало RNDN; теперь есть доступ к RNDZ / RNDU / RNDD,
  как у `set_round`. Реализация делит подпрограммы
  `mpf_sticky_below` / `mpf_round_up` / `mpf_add_one` с `set_prec`.

- **Публичные константы `ln2` и `e`.** `s21_mpf_ln2` и
  `s21_mpf_e` — отдельные символы API. `ln2` уже вычислялся
  внутри `log` как `2 · atanh(1/3)`; `e` — как `exp(1)`.
  Теперь доступны пользователю без обходных путей.

- **Тест субнормального `set_d`.** Минимальный денормализованный
  `5e-324` (битовая единица в младшем разряде) — предыдущее
  покрытие было только косвенным (`1e10`, `0.5`). Проверяется
  точное значение после `set_d`.

- **Фикс: argument reduction для больших тригонометрических
  аргументов.** `reduce_2pi` считал π на `wp = prec + 64` битах
  и работал с той же точностью. При `|x| ~ 2^E` вычитание
  `a − round(a/2π)·2π` сокращает `E` бит — точность результата
  падала до `wp − E`. При `prec = 256` (`wp = 320`) любой
  аргумент дальше `2^320` давал мусор:

  ```
  sin(1e30)  @256: терялось ~100 бит — print_d не видел, cmp видел
  sin(1e50)  @256: терялось ~166 бит
  sin(1e100) @256: терялось ~332 бита — возвращал +0 вместо -0.372
  ```

  Исправление: π запрашивается на `wp + E` бит, где
  `E = max(0, x->exp − 1)`. Верхняя граница
  `S21_MPF_MAX_ARG_BITS = 10000`; выше функция возвращает NaN
  (π на 10⁴ бит через формулу Мэчина — уже ~66 мс).
  Для `|x| < 2` поведение не меняется: `E = 0`, всё как было.

  Контракт `*_with_pi` обновлён: `pi->prec >= res->prec + 128 + E`.
  Меньшая точность π даёт `-1`.

  `test_trig_large_args`: 9 аргументов от `1` до `1e2000`,
  x парсится один раз на высокой точности, `sin`/`cos` считаются
  при `res->prec = 256` и `2048`, результаты сравниваются после
  RNDN-округления старшего. Плюс `sin(1e50000) = NaN`.

Тесты: **39 групп**, все зелёные. ULP-диагностика по-прежнему
показывает 0.0 везде.

## Сборка

Все команды запускаются из каталога `src/`:

```sh
cd src
make                     # статическая библиотека libs21_mpf.a
make test                # собрать и запустить unit-тесты
make repl                # интерактивная утилита s21_mpf_repl
make bench               # микробенчмарк s21_mpf_bench
make clang-format        # применить clang-format ко всем исходникам
make clang-format-check  # проверить форматирование (для CI, без правок)
make valgrind            # утечки памяти (memcheck)
make asan                # сборка с AddressSanitizer
make ubsan               # сборка с UndefinedBehaviorSanitizer
make gcov_report         # покрытие (lcov + genhtml)
make clean               # удаление артефактов
```

Альтернатива без `cd` — из корня проекта:

```sh
make -C src test
```

Компилятор: `gcc`, стандарт `-std=c11`, флаги `-Wall -Wextra -Werror -O2`.
Стиль кода задан в `.clang-format` (Google Style, отступ 2 пробела).

## Как устроено внутри

### Представление числа

```c
typedef struct {
  uint64_t *limbs;   /* мантисса, little-endian, limbs[0] — младшие 64 бита */
  int64_t   exp;     /* x = (-1)^sign · mant · 2^(exp − prec) */
  uint32_t  prec;    /* точность в битах */
  int       sign;    /* 0 = +, 1 = − */
  int       kind;    /* ZERO / NORMAL / INF / NAN */
} s21_mpf_t;
```

**Инварианты для NORMAL:** MSB мантиссы на позиции `prec − 1`,
биты выше `prec` нулевые, значение `x = (−1)^sign · mant · 2^(exp − prec)`.

**Специальные значения:** `ZERO` (хранит знак −0), `INF` (±), `NAN`.

### Нормализация и смена точности

`s21_mpf_normalize` приводит мантиссу к инварианту MSB@prec−1.
Сдвиги — единые функции `s21_mpf_shift_left_into` / `s21_mpf_shift_right_into`
с раздельно заданными `dst_count` / `src_count`.

`s21_mpf_set_prec` меняет точность на месте, сохраняя значение:
расширение — точно, сужение — RNDN. `s21_mpf_set_prec_round` —
то же самое, но с явным режимом округления. Обе разделяют
подпрограммы `mpf_sticky_below`, `mpf_round_up`, `mpf_add_one`.

### Стековые временные объекты

Обёртка `s21_mpf_stack_t` содержит `s21_mpf_t` и буфер
`uint64_t[S21_MPF_STACK_LIMBS]` (32 лимба = 2048 бит). Если рабочая
точность влезает — `limbs` указывает на стек; иначе `stack_init`
вызывает `calloc`. Освобождать через `s21_mpf_stack_clear`, не через
`s21_mpf_clear` (последний сделает `free()` от указателя на стек).

Применяется в `add`, `sub`, `div` (все три временных) и в `add_raw` /
`div_raw` для вспомогательных буферов.

### Scratch-пространство `mul_raw`

`mul_raw` требует три временных буфера: `xw` и `yw` на `wp = prec + 64`
лимбов, `temp` на `2·wp`. Раньше это были три `init2` плюс отдельный
`malloc` под произведение — четыре аллокации и четыре `free` на
каждый вызов. Внутри трансцендентных `mul_raw` вызывается сотни раз,
и аллокации становились заметной статьёй расхода при малых `prec`.

Теперь — один буфер `total = 2·l_wp + l_prod` лимбов, где `l_wp`
и `l_prod` считаются из `wp`. Если `total ≤ S21_MPF_MUL_SCRATCH_LIMBS`
(512 лимбов = 4 КБ), используется стековый массив и один `memset`.
Иначе — один `calloc(total)`.

`xw`, `yw`, `temp` конструируются как struct-initializers, указывающие
внутрь scratch. Никаких `init2` / `clear`: для стекового случая
освобождать нечего, для heap — один `free(base)`. Поле `temp.limbs`
служит приёмником `mul_mant`, так что отдельный `prod` не нужен.

Лимит 512 лимбов покрывает `prec` до ~8000. Выше идёт heap-ветка,
но всё равно одна аллокация вместо четырёх.

### Argument reduction в тригонометрии

`reduce_2pi(r, a, pi, wp)` сводит `a` к `(-π, π]`:

```
r = a − round(a / 2π) · 2π
```

Точность результата `r` ограничена точностью π. Если `a ≈ 2^E`,
то `round(a/2π) · 2π` имеет порядок `2^E`, и вычитание двух таких
чисел **сокращает `E` старших бит**: относительная точность результата
падает с `2^-wp` до `2^(E-wp)`.

Отсюда требование: для `|x| ≈ 2^E` нужна π на `wp + E` битах.
Хелпер `trig_extra_bits(x)` возвращает `max(0, x->exp − 1)`,
это значение добавляется к рабочей точности в `sin_impl`, `cos_impl`
и `tan`. При `E > S21_MPF_MAX_ARG_BITS = 10000` функция возвращает
NaN: π на 10⁴ битах через формулу Мэчина заняла бы ~66 мс, а
аргумент такой величины всё равно означает потерю всех значащих
цифр даже при сверхвысокой точности.

### Алгоритмы по операциям

| Операция | Подход | Рабочая точность |
|---|---|---|
| `add`, `sub` | выравнивание по `exp`, сложение с carry / вычитание с borrow; для разных знаков — через `cmp_abs` | `prec + 64` |
| `mul` | школьное умножение `mul_mant` (O(n²)) в scratch-буфере; финальное округление RNDN | `prec + 64` |
| `div` | алгоритм D Кнута: нормализация делителя, `n+1` итераций с оценкой `q̂`, уточнением и add-back | `prec + 64` |
| `sqrt` | метод Ньютона `x_{n+1} = (x_n + a/x_n)/2` с seed из `double` (~53 правильных бита) | `prec + 64` |
| `exp` | ряд Тейлора после halving до `|y| ≤ 2^-5`; `s` финальных квадратов | `prec + 64` |
| `log` | atanh-ряд: `m = 5` sqrt-итераций к `y ∈ [1, 2)`, затем `z = (y^(1/2^m)-1)/(y^(1/2^m)+1)` | `prec + 64` |
| `pi` | формула Мэчина | `prec + 64` |
| `sin`, `cos` | reduction по `2π` через `reduce_2pi`, затем ряд | `prec + 64 + max(0, x->exp − 1)` |
| `tan` | `sin(x) / cos(x)`; одна π на вызов | `prec + 64 + max(0, x->exp − 1)` |
| `atan` | reduction + степенной ряд; π только для `|x| > 1` | `prec + 64` |
| `asin` | `atan(x / √(1 − x²))` | `prec + 64` |
| `acos` | `π/2 − asin(x)` | `prec + 64` |
| `set_round` | RNDN / RNDZ / RNDU / RNDD | `dst->prec` |
| `set_prec`, `set_prec_round` | in-place смена точности | `prec` |

**Guard-биты `prec + 64`** защищают значащую часть результата
от накопленной ошибки округления.

**Ленивое π** — вычисляется один раз на верхнем уровне и передаётся
в `_impl`-варианты. Без глобального кэша в библиотеке: он нарушает
принцип «нет глобальных переменных» и порождает проблемы
thread-safety.

**Knuth D в `div`** — O(n²) лимбовых умножений вместо O(prec²)
битовых сдвигов старой реализации.

**Double seed в `sqrt`** — 64 старших бита мантиссы → `m_norm ∈ [1, 2)`,
`√(m_norm · 2^rem)` через libm, масштабирование `ldexp(half)`.
Экономит ~7 итераций Newton из ~14 при `prec = 4096`. Fallback
на `2^(exp/2 + 1)` при экстремальных `exp`.

**Sqrt reduction в `log`** — пять `sqrt` от `y ∈ [1, 2)` приводят
аргумент `atanh` к `z ≈ (y-1)/(2^m · (y+1))`. Ряд сходится за
~`wp / (2m+2)` членов вместо ~`wp / log₂(9)`. Пять `sqrt` при
`prec = 4096` стоят ~500 μs, экономят ~6 ms.

### Тригонометрия с явной π

Публичные `sin`/`cos`/`tan`/`atan`/`asin`/`acos` при каждом вызове
считают π заново. Для `prec = 4096` это порядка **12 мс** —
формула Мэчина требует ~900 членов ряда `atan(1/5)` и ~260 членов
`atan(1/239)`, каждый член — `mul_raw` на 65 лимбах. Сам ряд
sin/cos на той же точности занимает ~4 мс, то есть π доминирует
в три раза.

Если в цикле делается много тригонометрических вызовов, π стоит
посчитать один раз:

```c
uint32_t prec = 4096;
s21_mpf_t pi;
s21_mpf_init2(&pi, prec + 128);
s21_mpf_pi(&pi);

s21_mpf_t x, r;
s21_mpf_init2(&x, prec);
s21_mpf_init2(&r, prec);

for (int i = 0; i < 1000; i++) {
  s21_mpf_set_d(&x, i * 0.001);
  s21_mpf_sin_with_pi(&r, &x, &pi);   // без пересчёта π
}
```

Шесть публичных функций `*_with_pi` — тонкие обёртки над
существующими `_impl`-вариантами. Контракт:
`pi->prec >= res->prec + 128 + E`, где `E = max(0, x->exp − 1)` —
компенсация сокращения при `reduce_2pi`. Для `|x| < 2` сводится
к прежнему `+128`. Меньшая точность π даёт `-1`; при
`E > S21_MPF_MAX_ARG_BITS` результат — NaN.

REPL использует эту схему прозрачно: тригонометрические команды
держат одну π на текущую точность, сбрасывая кэш при `setprec`.

### I/O

**`set_str`** — посимвольный разбор целой и дробной частей
с накоплением мантиссы в `prec + 64` бит. Экспонента
применяется как `M · 10^E` (бинарное возведение в степень,
`log₂(|E|)` умножений). Финальное округление — RNDN.

**`get_str`** — оценка `E ≈ floor(log₁₀(x))`, масштабирование
`y = |x| / 10^E` на рабочей точности `n_digits · 4 + 192` бит,
нормализация в `[1, 10)`, извлечение цифр `d = floor(y)`.
Решение об округлении из остатка `y ∈ [0, 10)` — RNDN (ties-to-even),
RNDZ, RNDU, RNDD. Знак обрабатывается отдельно.

### История исправленных дефектов

**v1.0.0**: `cmp_abs` через `double` на разных `prec`;
`mul` при `prec`, не кратных 32.

**v1.1.0**: `cmp(0, x<0)`; `abs(-0)`; `set_d` субнормальных;
знак `tan` при `cos=0`; `sub_raw` через `add_raw`;
сдвиги с раздельными `dst_count`/`src_count`.

**v1.2.0**: только структурный рефакторинг.

**v1.3.0**: `set_prec` меняла `prec` без пересчёта `exp`;
`mpf_add_one` не обрабатывала перенос в бит `prec` при `prec % 64 != 0`.

**v1.4.0**: `print_d` переполнялась в `+inf` при `prec > 1024`.

**v1.5.0 – v1.9.0**: без дефектов.

**v1.10.0**: **обрезание ряда `exp`**. Жёсткий cap `n < 300`
в цикле Тейлора. При `prec ≥ ~3000` ряд требует больше членов
и молча обрезался. Найдено при попытке ускорить `exp` через
halving. Заменено на `max_terms = wp + 10`.

**v1.11.0**: **тихое проглатывание ошибки `div_raw`**. Публичный
`div` игнорировал возврат `div_raw` (0 / −1 при OOM). При сбое
`res` получал ноль вместо ошибки. Найдено при ревизии `return`
после правки `mul`. Теперь `rc` проверяется перед `set`.

**v1.12.0**: **потеря точности при `reduce_2pi` для больших
аргументов**. `sin`, `cos`, `tan` молча возвращали мусор для
`|x| ≥ 2^wp`. Найдено ручной проверкой `sin(1e100)` — `print_d`
показывал правдоподобное `-0.37`, а точное сравнение с 2048-битным
эталоном ловило расхождение в 332 бита. Исправлено расширением π
до `wp + E` и NaN за пределом `S21_MPF_MAX_ARG_BITS`.

## Точность и тестирование

### ULP-метрика

`test_ulp_diagnostics` — для каждой функции сравниваются результаты
при `prec = N` и `prec = 2N`. Gap в ULP младшей точности. Прогон
идёт по семи точностям `N = 32, 64, 128, 256, 512, 1024, 2048`.
Все результаты — 0.0, что подтверждает достаточность guard-битов.

Расширение до N = 2048 добавлено в v1.10.0 после того, как
баг с обрезанием ряда `exp` показал, что верхняя граница 256
не покрывает режимы, где ряд сходится медленнее.

### Тест больших аргументов

`test_trig_large_args` — отдельная регрессия под баг v1.12.0.
Проверяет `sin` и `cos` для `1, 10, 1000, 1e10, 1e30, 1e50, 1e100,
1e500, 1e2000`. Каждый аргумент парсится один раз на 2048-битной
точности; результаты считаются при `res->prec = 256` и
`res->prec = 2048`, старший приводится к младшему через RNDN,
сравнивается на равенство. Плюс `sin(1e50000) = NaN` — верхняя
граница `S21_MPF_MAX_ARG_BITS` работает.

### Теоретические оценки сложности

- `add`, `sub`, `cmp` — O(n) по числу лимбов;
- `mul` — O(n²), школьный алгоритм;
- `div` — O(n²) лимбовых умножений;
- `sqrt` — O(n²) на итерацию, итераций O(log n) (сокращается
  вдвое с seed из `double`);
- `exp` — O(n²·k), где `k ≈ wp/5` после halving;
- `log` — O(n²·k), где `k ≈ wp/(2m+2)` после sqrt reduction
  (`m = 5`);
- `sin`/`cos` — O(n²·k) по ряду плюс π Мэчина, если не передан
  через `*_with_pi`.

## Roadmap на будущее

- **Карацуба / Toom-Cook** для `mul`, **Ньютон** для `div` поверх
  быстрого `mul` — при `prec > 4096` школьный алгоритм становится
  узким местом. Карацуба начинает выигрывать примерно с
  `n ≈ 32–64` лимба (`prec ≈ 2048–4096`).
- **Binary splitting для atanh-ряда** в `log`. После Карацубы
  даёт O(N^1.585 · log N) вместо O(N³) по школьному умножению.
  Ожидаемое ускорение `log` ~2× в диапазоне 2048–8192.
- **AGM-логарифм** — потенциально 3–5× на `log`, но требует
  точной формулы из Sasaki-Kanada 1982 или Borwein & Borwein
  «Pi and the AGM». Оставлено на будущее, когда появится
  внешний источник.
- **`s21_mpf_repl`: кэш π с учётом E.** Сейчас `pi_cache_get`
  возвращает π ровно на `prec + 128`. Для больших аргументов
  (`sin 1e50` в REPL) `*_with_pi` вернёт -1, и REPL напечатает
  ошибку. Нужна правка `repl.c`: парсить аргумент, вычислить E,
  запросить π на `prec + 128 + E`.
- **Произвольные основания** (`base = 2, 8, 16`) в `set_str` / `get_str`.

## Мотивация

В `s21_math` мы делали `math.h` с точностью `long double`.
Финальная версия (v1.0.0) решала argument reduction problem
даже на Apple Silicon через double-double. Но предел всё равно
оставался: эффективная точность максимум ~226 бит.

`s21_mpfr` снимает это ограничение: точность задаётся
пользователем от 2 бит до миллионов. Это позволяет:

- Вычислять `sin(1e10)` с точностью `2^-1000`, а не `2^-16`.
- Реализовывать произвольную точность для криптографии
  (RSA, ECC) — числа длиной 2048, 4096 бит.
- Экспериментировать с произвольной точностью без потери
  контроля над форматом числа.
